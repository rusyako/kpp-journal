# План безопасного физического пилота (employeeNo `3818077855`)

Дата: 2026-11-13. Обозначения: **DOCUMENTED** · **VERIFIED ON DEVICE** · **NOT VERIFIED** — см. [MVP_IMPLEMENTATION.md](MVP_IMPLEMENTATION.md).

> **Техническая готовность ≠ разрешение.** Каждый шаг, помеченный 🔒, выполняется только после **отдельного явного
> разрешения** владельца оборудования (ИТ-специалиста школы) в момент выполнения. Ни один такой шаг не выполнялся.

## 0. Главный вывод для пилота

Все параметры удалённой проверки (`remoteCheckDoorEnabled`, `checkChannelType`, `needDeviceCheck`, `remoteCheckVerifyMode`,
`offlineDevCheckOpenDoorEnabled`, `remoteCheckTimeout`) и `httpHosts` — **глобальные для терминала** [FRT §14.6.3, с.423–428]
(DOCUMENTED). Фильтра по одному `employeeNo` нет. `remoteCheckUserTypeList` есть **только в примерах** [с.126, 129, 132],
не в API Reference; «if absent or empty, all person types require remote verification».

На действующем терминале все 2216 персон — `userType=normal` (выгрузка). Включение удалённой проверки там затронет **всех**:
при сбое kpp-journal — массовый отказ прохода. **Поэтому физический пилот — только на отдельном терминале (стенде)**
той же модели и прошивки либо на выделенной полосе, через которую ходит только тестовый участник.
Пилот на общем школьном терминале не проводится, пока стенд не докажет изоляцию (этап 3, проверка И-4).

```powershell

```

Выполняется чек-лист `DEVICE_CAPABILITIES.md` §2 (13 GET + один поиск `AcsEvent` по `3818077855`, без фото), по одному запросу
с паузой 1 с; при 401 — остановка (блокировка учётной записи после 5 ошибок на 30 мин, AUTHENTICATION.md §3).
Отчёт — `device-snapshots/<ip>-<время>/report.json` (в `.gitignore`), пароли вырезаны. Результаты занести в
`DEVICE_CAPABILITIES.md` с пометкой **HW**. Решение по матрице `DEVICE_CAPABILITIES.md` §3:
нет `isSupportRemoteCheck` → удалённая проверка невозможна, пилот останавливается; занят `httpHosts` → выяснить владельца.

## 4. Этап 2 — подготовка стенда 🔒

Обязательные условия:
1. **Отдельный терминал** той же модели/прошивки, не подключённый к школьному турникету (реле — на лампу/тестовый замок)
   **или** выделенная полоса, через которую в момент теста ходит только тестовый участник.
2. **Альтернативный безопасный маршрут** прохода открыт и проверен; аварийный выход и пожарная разблокировка — аппаратные,
   от kpp-journal не зависят (ACCESS_CONTROL.md §8).
3. Присутствуют: **инженер СКУД** (выполняет изменения и откат) и **сотрудник охраны** (контролирует проход). Вне учебного времени.
4. На стенде только персона `3818077855` (лицо — с согласия участника).
5. Сеть: стенд и сервер kpp-journal в одной изолированной сети/VLAN.

Действия:
1. Снимок «до» (только GET, сохранить в журнал теста, без паролей): `AcsCfg`, `AcsCfg/capabilities`, `httpHosts`,
   `httpHosts/capabilities`, `remoteCheck/capabilities`, `Door/param/1`, `AcsWorkStatus`.
2. Регистрация в kpp-journal (на устройство ничего не отправляет):
   ```powershell
   .\.venv\Scripts\python -m app.cli pilot-device stand --host <IP> --allowed-ips <IP> --credentials-env STAND --direction exit --response-mode sync
   .\.venv\Scripts\python -m app.cli pilot-setup
   ```
3. Запуск приёмника на IP в сети стенда: `uvicorn app.hikvision_gateway:app --host <IP сервера> --port 8090`.

## 5. Этап 3 — изменение настроек стенда 🔒 (выполняет инженер СКУД вручную)

Адаптер kpp-journal **не умеет** менять `AcsCfg`/`httpHosts` — это сознательное ограничение.

Порядок по документации [FRT §10.16.4.1, с.131–132]:
1. `GET /ISAPI/AccessControl/AcsCfg/capabilities?format=json` — убедиться, что есть `ISAPIListen`, `sync`, нужные поля.
2. Хост прослушивания: `POST /ISAPI/Event/notification/httpHosts` (или `PUT …/httpHosts/<id>`), URL
   `http://<IP сервера>:8090/hikvision/listen/stand`. Схема — [FRT §14.2.1, с.344–360].
3. `PUT /ISAPI/AccessControl/AcsCfg?format=json` — **только** поля удалённой проверки, остальные из снимка «до» без изменений:
   ```json
   {"AcsCfg": {"remoteCheckDoorEnabled": true, "checkChannelType": "ISAPIListen", "needDeviceCheck": true,
               "remoteCheckTimeout": 5, "remoteCheckVerifyMode": 2, "offlineDevCheckOpenDoorEnabled": false,
               "remoteCheckWithISAPIListen": "sync"}}
   ```
   ⚠ В схеме PUT API Reference [с.425–426] есть только `remoteCheckDoorEnabled`, `checkChannelType`, `channelIp`; прочие поля —
   из примеров §10.16. Сбрасываются ли непереданные поля — **не описано**: сразу после PUT сделать `GET AcsCfg` и сравнить со снимком.
4. kpp-journal: `HIKVISION_MODE=PILOT`, `HIKVISION_CONTROL_ENABLED=1`, `HIKVISION_CONTROL_DEVICES=stand`, перезапуск
   `api` и приёмника; на `/pilot` — «Включить пилот».

## 7. Критерии немедленной остановки

Любой отказ прохода не-тестовому человеку; открытие при DENY или без запроса; задержка > 2 с систематически;
сбой приёмника; неожиданные изменения в `GET AcsCfg` после PUT; 401 при диагностике.

## 8. Откат

**В kpp-journal (секунды, без доступа к терминалу):** на `/pilot` — «Выключить пилот» (все запросы → `failed`) и/или
`HIKVISION_MODE=SIMULATION` / `HIKVISION_CONTROL_ENABLED=0` + перезапуск. Это **закрывает** проход для пилотного терминала
(fail-closed), поэтому полный откат — на терминале:

**На терминале (инженер СКУД):**
1. `PUT /ISAPI/AccessControl/AcsCfg?format=json` со значениями из снимка «до» (как минимум `remoteCheckDoorEnabled: false`).
2. Вернуть `httpHosts` из снимка (удалить/восстановить добавленный хост).
3. Вернуть `doorRight`/`userType` персоны, если менялись в С-7/И-2.
4. `GET AcsCfg`, `GET httpHosts` → сравнить со снимком «до»; пройти по лицу тестовым участником — открывается локально.
5. Остановить приёмник; записать итог в журнал решений `README.md`.

## 9. Что требует отдельного разрешения

1. Любые сетевые запросы (даже GET) к школьным терминалам и к стенду — этап 1.
2. Изменение `AcsCfg`, `httpHosts`, `userType`, `doorRight`, `RightPlan` — только на стенде, этап 3.
3. Включение `HIKVISION_MODE=PILOT` и `HIKVISION_CONTROL_ENABLED=1`.
4. Применение миграции `0002` к production-БД и развёртывание ветки.
5. Любой шаг на действующем проходе — отдельный письменный план.
