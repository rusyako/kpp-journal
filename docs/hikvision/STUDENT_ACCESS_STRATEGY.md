# Стратегия доступа учеников: «опознаёт Hikvision, выпускает kpp-journal»

Дата: 2026-11-13. Обозначения: **IMPLEMENTED** · **TESTED** · **DOCUMENTED** · **VERIFIED ON DEVICE** · **NOT VERIFIED**.
Ничего из этого документа на оборудовании не проверялось.

## 1. Цель

* Ученик зарегистрирован в Hikvision, лицо распознаётся, `employeeNo` известен.
* Постоянного самостоятельного права **выхода** у ученика нет: выход только после проверки в kpp-journal.
* Другие категории (учителя, сотрудники) — свои политики. Вход и выход могут различаться.
* Без повторной регистрации лиц.

## 2. Что дают механизмы Hikvision

| Механизм | Что умеет | Подходит для «политики STUDENTS»? | Источник / статус |
|---|---|---|---|
| `belongGroup` | Привязка персоны к группе (до 4 групп), группа настраивается `GroupCfg/<groupID>` | **Нет.** Описан в разделе **Multi-Factor Authentication** (§10.13): группы нужны для режима «несколько человек подтверждают проход». Связи с удалённой проверкой в документации нет | [FRT §10.13.2.1–10.13.2.2, с.116] DOCUMENTED |
| `userType` | `normal`, `visitor`, `blackList`, `administrators` | Только как ключ для `remoteCheckUserTypeList`; отдельного типа «student» нет | [с.393, 410, 507] DOCUMENTED |
| `remoteCheckUserTypeList` | Удалённая проверка только для указанных типов; пусто/нет = все | Теоретически да (например, ученики — `visitor`), **но** поле есть только в примерах, не в API Reference; семантика `visitor` на устройстве не описана | [с.126, 129, 132] DOCUMENTED (частично); NOT VERIFIED |
| `doorRight` + `RightPlan`/`planTemplateNo` | Право на дверь по расписанию | Для «окон выхода» (сценарий A аудита): запись в пользователей терминала, нет мгновенной отмены | [§10.18, с.137–142] DOCUMENTED |
| Remote Verification на терминале | Решение платформы до открытия | **Да**, но параметры глобальны для терминала | [§10.16] DOCUMENTED |
| `remoteCheckVerifyMode` | Какие способы опознания идут на удалённую проверку | Глобально: например, только лицо (2), карты — локально | [с.127] DOCUMENTED |

Вывод: **политику «группа STUDENTS → обязательная внешняя проверка» на уровне персоны Hikvision штатно не предлагает.**
`belongGroup` для этого не предназначен. Единственный рычаг на уровне персоны — `userType` через `remoteCheckUserTypeList`,
поддержка которого на DS-K1T341CM V3.3.40 не подтверждена.

## 3. Варианты

### Вариант 1 (рекомендован): отдельные терминалы на выход + политика по категориям в kpp-journal

* На терминалах **выхода** удалённая проверка включена **для всех** (`remoteCheckUserTypeList` не используется).
* Терминалы **входа** остаются на локальных правах — вход учеников и сотрудников не зависит от kpp-journal.
* Категория определяется в kpp-journal (`hik_persons.kind`: `student` / `staff` / …), а не в терминале:
  * `staff` — ALLOW по своей политике (например, всегда, или в рабочее время);
  * `student` — ALLOW только при действующем разрешении (сегодня — эдвайзер; позже — подтверждение родителей).
* Плюсы: не зависит от недокументированного поля; новая категория — изменение в kpp-journal, без записи в терминал;
  лица и `employeeNo` не меняются → **повторная регистрация лиц не нужна**.
* Минусы и требования: выход сотрудников тоже зависит от доступности kpp-journal → нужны резервирование сервера,
  мониторинг задержки, и **ручной выпуск охраной** (кнопка/ключ турникета на посту, независимая от ПО); решение по
  `offlineDevCheckOpenDoorEnabled` для сценария «сервер недоступен» принимает школа (сейчас — `false`, fail-closed).
* Требует проверки: изоляция направления — терминал физически только на выход (ACCESS_CONTROL.md §1, как подключён
  турникет — неизвестно).

### Вариант 2: ученики как `visitor` + `remoteCheckUserTypeList=["visitor"]` — **выбран заказчиком для пилота (2026-11-13)**

План и проверки — [VISITOR_REMOTE_VERIFICATION_PLAN.md](VISITOR_REMOTE_VERIFICATION_PLAN.md). Риски ниже остаются в силе и
закрываются проверками на стенде.

* Удалённая проверка только для учеников; сотрудники (`normal`) проходят локально.
* Требует изменения `userType` у всех учеников (`UserInfo/Modify`, ~2216 записей — массовая запись в терминал).
  Сохранится ли лицо при изменении персоны — по документации лицо привязано к персоне через `employeeNo`/`FPID` [с.93, 368],
  удаляется только вместе с персоной [с.125]; **NOT VERIFIED**.
* Риск: если прошивка молча игнорирует поле → «absent or empty → all person types» → удалённая проверка для всех без
  готовности к этому. Семантика `visitor` (ограничения визитёров) не описана.
* Допустим только после проверок И-1…И-4 ([PILOT_TEST_PLAN.md](PILOT_TEST_PLAN.md) §6) на стенде.

### Вариант 3: окна выхода через расписания терминала (`RightPlan`)

* Без удалённой проверки: kpp-journal пишет ученику временное право на дверь выхода.
* Минусы: запись в действующий терминал на каждое разрешение, задержка синхронизации, нет мгновенной отмены, риск
  «забытого» окна. Только запасной вариант, если удалённая проверка не поддерживается.

### Отклонено

* `RemoteControl/door` после обычного события доступа — не авторизация, а безусловное открытие для того, кто рядом.
* `belongGroup` как политика удалённой проверки — не подтверждено документацией.
* Verification by Platform Only (`needDeviceCheck=false`) — терминал не аутентифицирует локально, `employeeNo` по лицу не гарантирован.

## 4. Вход и выход

| Направление | Учащиеся | Сотрудники | Как |
|---|---|---|---|
| Вход | локальные права терминала | локальные права | терминалы входа без удалённой проверки |
| Выход | только ALLOW kpp-journal | политика kpp-journal (вариант 1) или локально (вариант 2) | терминалы выхода с удалённой проверкой |

Decision Engine уже отклоняет запросы с терминалов не «на выход» (`wrong_direction`) — **IMPLEMENTED, TESTED**.
