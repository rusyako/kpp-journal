# Пользователи, employeeNo, лица, карты, права

Источники — см. [README.md](README.md#обозначения-источников).
⚠ Все операции записи/удаления ниже **запрещены** на действующих терминалах без отдельного разрешения (см. `README.md` §Безопасность).

## 1. employeeNo

* Уникальный идентификатор персоны для всех учётных данных (карта, отпечаток, лицо, радужка) [FRT §10.15.2.1, с.118].
* Длина/набор символов — по `EmployeeNoInfo` (`employeeNo`, `characterType`, `isSupportCompress`) в `GET /ISAPI/AccessControl/capabilities`;
  «Generally, devices support up to 32 bytes and any type of characters» [с.118].
* В событиях — `employeeNoString` (приоритетно) и `employeeNo` (int) [с.409].
* **HW:** на терминале 192.168.4.49 все 2216 `employeeNo` — 10-значные строки (пример тестового: `"3818077855"`), `userType = "normal"`,
  `doorRight = "1"`, `RightPlan = [{doorNo:1, planTemplateNo:"<1|21|23|24|…>"}]`, `Valid.enable = true` (`hikvision_users.json`).

Тестовая запись (из выгрузки, без ФИО): `employeeNo "3818077855"`, `userType normal`, `Valid 2025-08-12T13:28:17 … 2035-08-12T23:59:59`,
`doorRight "1"`, `planTemplateNo "1"`, `numOfFace 1`, `numOfCard 1`.

## 2. Персоны (UserInfo) [FRT §10.15, с.117–125]

| Операция | Запрос | Проверка поддержки | Стр. |
|---|---|---|---|
| Количество | `GET /ISAPI/AccessControl/UserInfo/Count?format=json` → `userNumber` | `supportFunction` содержит `get` | 120 |
| Поиск (постранично) | `POST /ISAPI/AccessControl/UserInfo/Search?format=json` | то же | 120 |
| Применить (создать или изменить) | `PUT /ISAPI/AccessControl/UserInfo/SetUp?format=json` | `setUp` | 121 |
| Добавить (ошибка, если есть) | `POST /ISAPI/AccessControl/UserInfo/Record?format=json` | `post` | 122 |
| Изменить (ошибка, если нет) | `PUT /ISAPI/AccessControl/UserInfo/Modify?format=json` | `put` | 123 |
| Удалить (асинхронно) | `PUT /ISAPI/AccessControl/UserInfoDetail/Delete?format=json` + `GET …/DeleteProcess` | `isSupportUserInfoDetailDelete` | 124; API 502–505 |
| Возможности | `GET /ISAPI/AccessControl/UserInfo/capabilities?format=json` → `supportFunction`, `maxRecordNum` | — | 119–120 |

«When the person is deleted, the information on the credentials (card, fingerprint, face picture, iris) linked via the person ID will also be deleted» [с.125].

**Схемы запросов/ответов `UserInfo/*` в API Reference этого документа нет** (есть только `UserInfo/asyncImportDatasTasks` [с.505–510] и `UserInfoDetail/Delete`).
Рабочий формат поиска — из нашего скрипта (**HW**, `export_hikvision_users.py:244-250`):
```json
{"UserInfoSearchCond": {"searchID": "<uuid>", "searchResultPosition": 0, "maxResults": 30}}
```
Поиск одного пользователя по `employeeNo` (например, `EmployeeNoList`) — формат **не подтверждён** документацией набора; проверить по `UserInfo/capabilities`.

Типы персон (`userType`): `normal`, `visitor`, `blackList`, `administrators` [с.393]; в асинхронном импорте — `normal`, `visitor`, `blackList` [с.507].

## 3. Лица [FRT §10.10, с.89–97; API §14.4, с.361–379]

* Персона должна существовать до добавления лица; библиотека лиц `FDID = 1` (видимый свет) [с.89].
* Добавить: `POST /ISAPI/Intelligent/FDLib/FaceDataRecord?format=json` [с.368]; применить: `PUT …/FDSetUp` [с.377]; поиск: `POST …/FDSearch` [с.375];
  удалить: `PUT …/FDSearch/Delete?format=json&FDID=&faceLibType=` [с.373]. Связь с персоной — через `FPID` (запись лица) и `employeeNo` (персона) [с.93]; «if it is generated by the device automatically, it is the same as the employee No.» [с.368].
* В kpp-journal шаблоны/фото лиц **не храним** (решение аудита §11.3; персональные данные несовершеннолетних).

## 4. Карты [FRT §10.6, с.73–82]
`/ISAPI/AccessControl/CardInfo/*` (Search/Record/Modify/SetUp/Delete) — потоки на с.74–81; схем в API Reference набора нет.

## 5. Права доступа и расписания [FRT §10.18, с.137–142]

* Права = связь персоны с дверью (`doorRight`) + шаблон расписания (`RightPlan.planTemplateNo`).
  «Configuring schedules of persons' access permission is required, or the related persons cannot access» [с.137].
* Шаблон: 1 недельное расписание + 4 группы праздников; неделя — 8 интервалов в день; праздники имеют приоритет [с.137].
* API: `UserRightPlanTemplate/<id>`, `UserRightWeekPlanCfg/<id>` [с.139–140; API §14.6.9, с.492–501], `UserRightHolidayGroupCfg/<id>`, `UserRightHolidayPlanCfg/<id>` [с.141–142].
* Срок действия персоны — `Valid.enable/beginTime/endTime` (видно в выгрузке; в API Reference набора — только в asyncImport [с.507]).

### Почему не управлять разрешениями на выход через права терминала
Аудит (`HTA_STUDENT_RELEASE_TECHNICAL_AUDIT.md` §11.2, сценарий A) рассматривал загрузку временных окон в терминал. Для нашей цели
(разрешение родителей, мгновенная отмена) это хуже удалённой проверки: требует **записи** в пользователей действующего терминала,
задержка синхронизации, риск «забытого» окна. Сценарий A остаётся запасным, если удалённая проверка не поддерживается.
