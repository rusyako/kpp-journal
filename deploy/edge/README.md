# Доступ эдвайзеров из интернета через внешний сервер

## Зачем это нужно

Журнал работает на **основном сервере** в локальной сети. КПП и админка открывают его по внутреннему IP.
Эдвайзеры в эту сеть попасть не могут:

- в гостевой сети устройства изолированы друг от друга, там есть только интернет;
- доступ к рабочей сети есть не у всех эдвайзеров.

Поэтому страницу эдвайзера открываем через **внешний сервер с белым IP**.

## Как это устроено

```
 Эдвайзер (Telegram: мобильный интернет, гостевой Wi-Fi, дом)
        │  HTTPS  https://kpp.hta.kz/advisor
        ▼
 ┌──────────────────────────── Внешний сервер (белый IP) ────────────────────────────┐
 │  Caddy: HTTPS-сертификат + фильтр адресов. Базы и данных здесь НЕТ                 │
 │  пропускает: страницы сайта, /api/me, /api/advisor/*, /api/ws                      │
 │  закрывает:  /api/admin, /api/day, /api/exits, /api/reports, /api/auth/login …      │
 └───────────────────────────────────────┬────────────────────────────────────────────┘
                                         │  WireGuard-туннель (шифрованный)
                                         │  10.77.0.1  ⇄  10.77.0.2
                                         │  подключается ОСНОВНОЙ сервер, изнутри наружу
 ┌───────────────────────────────────────┴──────────── Основной сервер ──────────────┐
 │  API + база + Telegram-бот (как сейчас)                                            │
 │  КПП и админка — по локальной сети: http://<внутренний IP>:8090                     │
 └────────────────────────────────────────────────────────────────────────────────────┘
```

### Почему внешний сервер просто передаёт запросы, а не держит копию сайта

Странице эдвайзера нужно не только отправлять разрешения, но и видеть своих учеников и отметку «🚪 вышел» сразу, как только охрана её поставит.
Копия сайта на внешнем сервере была бы отдельной программой с отдельной базой, которую пришлось бы синхронизировать.
Если внешний сервер только передаёт запросы, то:

- данные детей хранятся только на основном сервере, на внешнем нет ни базы, ни копий;
- программа одна, обновлять её нужно в одном месте;
- если внешний сервер или интернет отключится, КПП и админка продолжат работать по локальной сети.

### Почему туннель подключается из локальной сети

Основной сервер сам подключается к внешнему по UDP-порту 51820, как обычная программа, которая ходит в интернет.
Поэтому в роутере локальной сети не нужно открывать порты и делать проброс: снаружи локальная сеть остаётся закрытой.
По туннелю внешний сервер видит только порт API основного сервера. SSH и всё остальное закрыто (см. `PostUp` в `wg0.local.conf.example`).

### Почему вход только через Telegram

На внешнем сервере закрыт `/api/auth/login`, поэтому войти по логину и паролю из интернета нельзя.
Эдвайзер открывает страницу кнопкой **«📝 Разрешения на выход»** в боте. Telegram сам подтверждает, кто это (подпись `initData`), пароль не нужен.
Даже если чей-то пароль, например охраны, утечёт, из интернета им не воспользоваться.
Охране и админке снаружи всё равно ничего не доступно: их адреса API закрыты.

### Почему боту не нужен белый IP

Бот сам раз в несколько секунд спрашивает у Telegram, есть ли новые сообщения (polling). Уведомления «🚪 вышел» и отчёт он тоже отправляет сам.
Ему нужен только выход в интернет, поэтому бот остаётся на основном сервере рядом с базой.
Белый IP и HTTPS нужны только самой странице Mini App: Telegram открывает её строго по `https://` с настоящим сертификатом.

## Что нужно заранее

| Что | Зачем |
|---|---|
| Внешний сервер Linux (Ubuntu 22.04/24.04) с белым IP | HTTPS и конец туннеля |
| Домен, например `kpp.hta.kz`, с A-записью на белый IP | Сертификат Let's Encrypt, адрес Mini App |
| Открытые порты на внешнем сервере: TCP 80, 443 и UDP 51820 | 80/443 — сайт и выпуск сертификата, 51820 — туннель |
| У основного сервера есть выход в интернет по UDP 51820 | Туннель. Если UDP закрыт, см. «Если UDP закрыт» ниже |
| Основной сервер Linux с Docker | Там уже работает журнал |

Адреса в туннеле `10.77.0.1` (внешний) и `10.77.0.2` (основной) можно оставить как есть, если в локальной сети нет своей подсети `10.77.0.x`.

## Шаг 1. WireGuard на обоих серверах

На **каждом** сервере установите WireGuard и создайте пару ключей:

```bash
sudo apt install -y wireguard
cd /etc/wireguard && umask 077
wg genkey | sudo tee server.key | wg pubkey | sudo tee server.pub
```

Получится два файла: `server.key` — секретный ключ, он никуда не передаётся; `server.pub` — открытый ключ, его можно отправить на другой сервер.
Дальше открытый ключ внешнего сервера называем `edge.pub`, основного — `local.pub`.

**Внешний сервер:** скопируйте `wg0.edge.conf.example` в `/etc/wireguard/wg0.conf` и подставьте свой `server.key` и `local.pub`.
**Основной сервер:** скопируйте `wg0.local.conf.example` в `/etc/wireguard/wg0.conf` и подставьте свой `server.key`, `edge.pub` и белый IP внешнего сервера.

На обоих серверах включите туннель с автозапуском:

```bash
sudo systemctl enable --now wg-quick@wg0
```

Проверка со основного сервера:

```bash
ping -c 3 10.77.0.1
```

Если ping проходит, туннель работает. Команда `sudo wg show` покажет `latest handshake` — время последней связи между серверами.

## Шаг 2. Журнал на основном сервере

В `deploy/.env` основного сервера:

```ini
PUBLIC_URL=https://kpp.hta.kz          # адрес внешнего сервера: из него бот делает кнопку Mini App
API_BIND=0.0.0.0                        # API доступен из локальной сети и из туннеля
API_PORT=8090
COOKIE_SECURE=0                         # в локальной сети вход идёт по http
FORWARDED_ALLOW_IPS=10.77.0.1           # верить X-Forwarded-For только от внешнего сервера
SECRET_KEY=<openssl rand -hex 32>
TELEGRAM_BOT_TOKEN=...
TELEGRAM_BOT_USERNAME=...
```

Запустите сервисы **без** `caddy`, потому что HTTPS теперь делает внешний сервер:

```bash
cd deploy && docker compose up -d --build db api bot backup
```

Проверка с внешнего сервера: должен прийти ответ `{"ok":true}`.

```bash
curl http://10.77.0.2:8090/api/health
```

> **Зачем `FORWARDED_ALLOW_IPS`.** Все запросы из интернета приходят к API от одного адреса, 10.77.0.1.
> Настоящий IP эдвайзера Caddy передаёт в заголовке `X-Forwarded-For`. Этому заголовку можно верить, только если он пришёл от нашего Caddy.
> Иначе любой пользователь локальной сети сможет подставить чужой IP и обойти лимит попыток входа.

## Шаг 3. Caddy на внешнем сервере

Скопируйте на внешний сервер папку `deploy/edge` (нужны только `Caddyfile`, `docker-compose.yml`, `.env.example`). Затем:

```bash
cd deploy/edge
cp .env.example .env      # укажите DOMAIN и UPSTREAM
docker compose up -d
```

При первом запуске Caddy сам получит сертификат Let's Encrypt. Для этого A-запись домена уже должна указывать на сервер, а порт 80 должен быть открыт.

Проверка с любого компьютера в интернете:

```bash
curl https://kpp.hta.kz/api/health            # {"ok":true}
curl -i https://kpp.hta.kz/api/day            # 404: КПП снаружи закрыт
curl -i https://kpp.hta.kz/api/auth/login     # 404: вход по паролю снаружи закрыт
```

## Шаг 4. Бот и эдвайзеры

1. Перезапустите бота: `docker compose restart bot`. При старте он сам ставит кнопку меню «Разрешения» с адресом `PUBLIC_URL/advisor`. Если в логе бота есть «PUBLIC_URL не https», значит, в `.env` указан адрес без `https://`.
2. В админке (`http://<внутренний IP>:8090/admin`) → «Пользователи» → «Приглашение» для каждого эдвайзера. Отправьте ему ссылку.
3. Эдвайзер открывает ссылку, нажимает **Start** в боте, затем **«📝 Разрешения на выход»**.
4. В админке «Проверка»: пункт «Эдвайзеры подключили Telegram» должен быть ✅.

## Если UDP закрыт: SSH-туннель вместо WireGuard

Если файрвол локальной сети не пропускает UDP 51820, туннель можно сделать через SSH (TCP 22 или 443). Он работает медленнее WireGuard, но для страницы эдвайзеров этого достаточно.

На основном сервере:

```bash
sudo apt install -y autossh
# ключ без пароля, его открытую часть добавить в ~tunnel/.ssh/authorized_keys на внешнем сервере
autossh -M 0 -N -o ServerAliveInterval=30 -o ExitOnForwardFailure=yes \
  -R 127.0.0.1:18090:127.0.0.1:8090 tunnel@<белый IP>
```

Чтобы туннель поднимался после перезагрузки, его нужно оформить как сервис systemd.
На внешнем сервере в `deploy/edge/.env` укажите `UPSTREAM=127.0.0.1:18090`.
В этом варианте запросы приходят к API от адреса Docker-шлюза, поэтому оставьте `FORWARDED_ALLOW_IPS` пустым и не открывайте `API_BIND=0.0.0.0` для сети, где есть посторонние.

## Что будет, если…

| Ситуация | Что произойдёт |
|---|---|
| Пропал интернет в локальной сети | КПП и админка работают. Эдвайзеры временно не могут открыть страницу, уведомления «🚪» придут, когда связь вернётся (если Telegram успеет их принять) |
| Упал внешний сервер | То же самое: локальная сеть работает, эдвайзеры ждут |
| Взломали внешний сервер | Данных на нём нет. Через туннель доступен только порт API, а он требует вход. Смените ключи WireGuard и SECRET_KEY |
| Эдвайзер уволился | Админка → пользователь → снять «Доступ включён». Telegram-вход перестаёт работать сразу |

## Обслуживание

- Обновления журнала ставятся только на основном сервере, внешний трогать не нужно.
- Caddy продлевает сертификат сам.
- Состояние туннеля: `sudo wg show` (на любом сервере). Если `latest handshake` старше 2–3 минут, связи нет.
